# ADR 0009. Согласование версий Go API ядра и платформы

Статус: proposed.
Дата: 6 ноября 2026 года.

## Контекст

[Архитектура ядра](../architecture.md) предлагает подключать ядро как Go-модуль к платформе, сохраняя локальный CLI. Разделение репозиториев не требует сетевого сервиса. Версии интерфейсов ядра и платформы нужно согласовывать. Сейчас описана архитектура, а публичные Go-пакеты, выпуски и автоматические проверки совместимости ещё не реализованы.

## Варианты

| Вариант | Преимущества | Ограничения |
| --- | --- | --- |
| Платформа следует за текущей веткой ядра | Быстрые совместные изменения | Неявная зависимость и трудно повторяемая сборка |
| Платформа закрепляет конкретную версию модуля, обновления проходят совместную проверку | Проверяемая пара версий и независимая история репозиториев | Требуется порядок выпуска и обновления зависимости |
| Вернуть ядро и платформу в один репозиторий | Проще атомарно менять вызывающий код | Меняет принятую организацию проекта и не устраняет версионирование сохранённых данных |
| Ввести отдельный сетевой API | Независимое развёртывание | Добавляет протокол, эксплуатацию и миграции без необходимости для MVP |

## Предлагаемое решение и обоснование

Предлагается закрепление конкретной версии Go-модуля ядра в платформе. На стадии прототипа допустима явно закреплённая ревизия до появления выпусков. Обычная сборка платформы не должна зависеть от незаписанного состояния соседней рабочей копии.

Предлагается вести версии модуля по схеме major.minor.patch и до объявления стабильного контракта использовать ветку версий 0.x. В этот период несовместимое изменение должно быть явно помечено в описании выпуска и сопровождаться согласованным изменением платформы. Сам номер версии не считается доказательством совместимости. Точное имя модуля, первая версия и политика после стабилизации остаются открытыми.

Публичным контрактом предлагается считать операции предметной модели, передаваемые типы, интерфейсы адаптеров, категории ошибок и наблюдаемые инварианты. Изменение смысла операции или правил ошибок требует такой же оценки совместимости, как изменение её сигнатуры. Внутренние детали хранения не должны становиться обязательными для клиента.

Версию Go-модуля следует отличать от версий манифеста и других сохраняемых форматов. Обновление библиотеки не должно молча переинтерпретировать старые записи. Для каждой поддерживаемой версии формата необходимо явно указать возможность чтения и записи. Неподдерживаемая версия должна давать диагностическую ошибку. Механизм миграции и политика чтения исторических данных требуют отдельного решения, автоматическая перезапись неизменяемой истории здесь не предлагается.

## Предлагаемый порядок изменения интерфейса

1. В ядре описать изменённый контракт, затронутые форматы и способ обновления клиента. Обновить соответствующий ADR при изменении архитектурного решения.
2. Проверить операции ядра и локальный CLI, включая прежние поддерживаемые записи и поведение ошибок.
3. Проверить платформу с конкретной кандидатной ревизией ядра: сборку, адаптеры и полный ограниченный сценарий публикации, снимка, регистрации, сравнения и плана восстановления.
4. После успешной проверки выпустить зафиксированную версию ядра и отдельным изменением закрепить её в платформе. В описании обновления указать проверенную пару версий и ограничения.
5. Повторить необходимые проверки платформы с окончательной зависимостью. Не объявлять другие сочетания версий поддерживаемыми без проверки.

Локальная подмена модуля допустима как временный инструмент разработки. Её нельзя считать подтверждением сборки с опубликованной зависимостью. Процедура выпуска не требует одновременной публикации обоих репозиториев или обязательного CI на первом шаге, но результаты проверки выбранной пары должны быть записаны.

## Последствия

Закреплённая зависимость позволяет воспроизвести выбранное сочетание кода и отделяет выпуск ядра от обновления платформы. За это приходится платить проверкой адаптеров и поддерживаемых форматов при каждом затрагивающем их изменении. Сборка сама по себе не проверяет сохранение предметных инвариантов.

Возврат к прежней версии зависимости не гарантирует возможность чтения данных, записанных новой версией. Перед откатом потребуется оценка совместимости форматов. Контрактные проверки и матрица совместимости пока являются предлагаемыми действиями, а не существующей инфраструктурой.

## Открытые вопросы

- Какое имя модуля и какие пакеты считать публичными после первого прототипа?
- Когда объявлять стабильный API и сколько прежних версий форматов поддерживать?
- Какие проверки совместимости достаточны для проверки учебного прототипа?
- Где хранить сведения о проверенной паре версий: в документации платформы, журнале выпусков или отдельной матрице?
- Потребуется ли сборке доступ к закрытым зависимостям или тестовым материалам и как предоставить его без сохранения учётных данных в репозитории?
