# Проверка интеграции первого горизонта

Основание проверки: main `e1c371529ccb51c759dc17c7b894b2ccaa9dbd5a`,
срезы объектов, dataset, snapshot и run. Это локальный инженерный прототип,
не свидетельство переносимости вычисления или научной воспроизводимости.

## Выполненные проверки

В `cmd/smlops/integration_test.go` отдельные процессы CLI используют чистый
временный каталог. Тест создаёт repository, записывает и считывает объект,
публикует dataset, snapshot и две отдельные попытки, повторяет регистрацию,
проверяет закреплённую страницу и неизменность ранее полученной записи. Два
конкурирующих процесса с одной ревизией ссылки дают один успех и один conflict.
Неверная ссылка на запуск другого снимка и неизвестное наблюдение отклоняются.
После удаления объекта проверяются успешный retry и отказ новых публикаций;
затем при повреждении байтов той же длины проверяется integrity для входа и
выхода. Отказы не увеличивают sequence. Тест использует один процессный
сценарий гонки, а не доказывает отсутствие гонок при всех нагрузках.

`catalog/experiment_test.go` и `catalog/catalog_test.go` дополнительно проверяют
Go API, типизированные значения, условия, прерванную попытку, изоляцию View,
целостность каталога, повторы, CAS и границы фиксации. Тесты CLI проверяют
обработку команд и состояние отказов. Для повторения проверок нужен Go 1.27.3:

```sh
go test -count=1 ./...
go test -race -count=1 ./...
go vet ./...
go build -o /tmp/smlops ./cmd/smlops
```

Проверки Wine запускаются отдельно по `.github/workflows/wine.yml`; они относятся
к самостоятельному учебному примеру и не означают его интеграцию с каталогом.
Существующий формат каталога v1 и локальные гарантии описаны в
[контрактах](contracts-v1.md). Проверка хешей не подтверждает происхождение кода,
полноту зависимостей или факт выполнения. Внешние материалы не загружаются;
устойчивость к потере питания, сетевые файловые системы и недоверенный владелец
не проверены и не гарантируются. Отсутствие всего каталога нельзя отличить от
отсутствия инициализации. ADR остаются proposed.

## Историческая очередь на момент проверки #7

Перечень ниже сохранён как исторический контекст. Совместная проверка уже
реализованных Diff и плана восстановления описана в [отчёте #17](diff-recovery-validation.md).

Это направления для уточнения, а не заранее утверждённые сроки или созданные
Issues. Оценки предварительные: диапазоны и зависимости пересматриваются после
проверки контрактов и детализации приёмки.

1. **Структурный Diff.** Сравнивать dataset, snapshot и run одного вида по
   проекциям контракта v1, сохраняя различия типов, отсутствующих полей и
   несовместимости метрик между профилями. Зависимость: текущие схемы и
   проверенный каталог. Приёмка: симметрия added/removed, типизированное
   сравнение, несовместимые метрики и независимая проверка примеров. Оценка
   6–12 часов активной работы; неопределённость связана с детализацией API и
   ошибок, оценка не является обещанием.
2. **План восстановления.** Проверять объявленные материалы снимка и выдавать
   статусы, blockers и план без сетевого разрешения зависимостей и исполнения.
   Зависимость: snapshot/run и действующие контракты восстановления; Diff не
   является обязательной технической зависимостью. Приёмка: missing, corrupt,
   io_error и unchecked обрабатываются согласно required; результаты проверки
   не выдаются за гарантию будущей доступности. Оценка 8–16 часов; наибольшая
   неопределённость — безопасная материализация путей и отказные сценарии.
3. **Один доверенный повторный запуск.** После плана определить узкий сценарий
   подготовки среды, исполнения и регистрации нового run со ссылкой на исходный.
   Зависимость: проверенный план, согласованный учебный пайплайн и заранее
   определённые метрики и допуски. Приёмка и оценка требуют отдельной постановки;
   сроки и трудоёмкость сейчас не определены.

Сверка GitHub на момент подготовки: самостоятельных Issues для Diff и плана
восстановления нет; #7 содержит задачу уточнения следующей очереди. Создание новых
Issues и назначение сроков в этот срез не входят.
