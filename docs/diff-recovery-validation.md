# Совместная проверка Diff и плана восстановления

Проверка для Issue #17 выполнена 2026-11-10 на базе main
`63e9e7f4d30734792ebeed7cd2ceeb43686f168a` с новым интеграционным тестом
`cmd/smlops/diff_recovery_integration_test.go`. Это инженерная проверка на
временном локальном хранилище, не ML-эксперимент и не доказательство научной
воспроизводимости.

## Сценарий и результат

Тест создаёт реальные объекты и одну историю через Go API: исходные dataset,
snapshot и run с выходным объектом, затем новую версию данных, снимок с новым
значением параметра и новый run. Ссылки `data` и `latest` перемещаются к новым
версиям. Сравнение запусков в обоих направлениях выполняется через Go API и
отдельные процессы CLI; проверяются направление значения параметра, добавление
и удаление результата и совпадение JSON-ответов. Отсутствующая запись даёт
`not_found` в обеих поверхностях.

План исходного запуска через обе поверхности продолжает указывать на исходный
снимок, входной dataset и значение параметра при обновлённых ссылках. Удаление
обязательного входного объекта даёт `missing` и blocker; возврат точных байтов —
`verified`; замена байтами той же длины — `corrupt` и blocker; устранение порчи —
`verified`; повторная потеря — `missing`. Отсутствие необязательного исходного
выхода не блокирует готовность обязательных материалов. `runtime_ready`,
`execution` и `numerical_agreement` остаются `unchecked` на каждом этапе.

После каждого сравнения, плана и проверенного отказа тест сверяет побайтно
`metadata/catalog.json`, sequence, все шесть записей, обе ссылки, сохранённые
операции и receipts, а также текущее содержимое и отсутствие объектов. Для
сравнения планов исключаются различия времени проверок: каждый вызов проводит
проверку заново. Удаление, повреждение и восстановление байтов выполняет сам тест
от имени доверенного владельца временного хранилища. Продукт не исправляет
повреждённые объекты автоматически, а Diff и PlanRecovery не изменяют объекты
или историю. Результат плана описывает состояние на момент проверки, не резервирует
материалы и не подтверждает полноту условий, исполнение или численное согласие.

## Выполненные команды

Использован Go 1.27.3 из локального toolchain. Завершились успешно:

```sh
go test -count=1 ./...
go test -race -count=1 ./...
go vet ./...
go build -o /tmp/smlops-issue17 ./cmd/smlops
```

Отдельно с Python из подготовленного Wine venv выполнен workflow
`.github/workflows/wine.yml`: `python -m unittest discover -s examples/wine -p
 'test_*.py'` — 9 тестов, OK; две копии примера запущены с `run --phase
validation` в отдельные временные каталоги, затем сравнены командой `compare`.
Обе команды run завершились успешно, compare вернул `conditions: equal`,
`execution: valid`, `materials: equal`, `numerical: pass`. Это проверка
самостоятельного учебного примера, не его интеграция с каталогом; основные
эксперименты не запускались, исходные evidence и протокол не изменялись.
Повторить шаги копирования, run и compare можно по `.github/workflows/wine.yml`,
заменив пути `/tmp/wine-a`, `/tmp/wine-b`, `/tmp/result-a`, `/tmp/result-b` на
новые пустые временные каталоги.
