# План итоговой проверки и сравнения Wine

Версия 1, 2026-11-11. Задача #24. Это предварительно фиксируемая методика,
а не результаты испытаний. ADR остаются proposed. Основные случаи #25 разрешены
только после независимого ревью, включения этой версии в main и фиксации SHA
исполняющего стенда. Изменять frozen-протокол Wine ради исхода запрещено.

## Вопрос и граница

Можно ли из сохранённых материалов старого Wine C=1.0 получить его условия,
выполнить отдельный запуск и объяснить результат при уже существующем C=2.0?
Выявляет ли выбранный путь восстановления потерю или порчу обязательного
материала до обучения, сохраняя прежнюю историю?

Сравниваются две конфигурации одного локального пользователя на одном хосте:

1. Scientific MLOps Core с локальным каталогом/объектами и существующим внешним
   examples/wine_catalog/repeat.py. Платформа используется для просмотра,
   исполнителем она не является.
2. Git + DVC + MLflow: Git фиксирует код/условия, DVC хранит данные, wheels и
   выходы через отдельный локальный remote, MLflow регистрирует отдельные
   попытки и артефакты в локальном SQLite/файловом хранилище. Общий внешний
   адаптер связывает их и проверяет фактическую среду.

Это одна составная альтернатива, закрывающая версии материалов и учёт запусков.
DVC выбран за пересечение с восстановлением и pipeline reproduction, MLflow -
за отдельные записи попыток. DataLad и ClearML остаются допустимыми кандидатами
для отдельного исследования; их неустановка не означает отсутствие функций
или худший результат. Рейтинг продуктов, время освоения человеком, скорость,
стоимость хранения, масштабируемость, переносимость и научная новизна здесь
не измеряются. Один инженерный проход не даёт статистических оценок.

Отключить DVC analytics/update check и отправку в Studio:

Все установки инструментария выполняются до измеряемого прохода.
Управляющие зависимости не устанавливать в среду Wine.

Для DVC используется native pipeline: dvc repro --force --no-run-cache,
затем git add для дескрипторов/метрик и dvc exp save с уникальным именем
попытки. Именно эта цепочка проверена синтетически. Флаг --no-run-cache
не передавать dvc exp run: DVC 3.67.1 его там отвергает. Это установочный
smoke, не измеренный случай Wine. Факт выполнения доказывается
новым UUID Wine, реальным дочерним процессом и пятью вновь созданными выходами.
Параметры опыта могут совпасть; повтор не обязан создавать новую идентичность
условий. Нативные refs/experiments сохраняются явно, обычный Git clone сам
по себе не считается переносом скрытых refs DVC. Историческое состояние
материализуется в именованную Git-ветку до удаления исходной рабочей копии.
Stage output одноразовый и не содержит source outputs: DVC может удалять
объявленный output перед выполнением. Source artifacts хранятся отдельно.
При отказе до stage MLflow/harness сохраняют failed attempt независимо от
возможности создать DVC experiment; отсутствие такого experiment не скрывается.

## Одинаковые материалы и доверенная граница

Обе стороны получают один и тот же существующий reference из Wine main-v1,
исходный bundle, семь wheels по requirements.lock и сохранённое описание
исходной среды. Импорт исходного результата помечается caller_reported;
он не является новым выполнением и не подтверждает текущую среду.

До случаев сохранить общий inventory: относительный путь, назначение,
required/optional, SHA-256 и размер каждого файла. Состав обязательных файлов
следует из проверенного Wine manifest, dataset, reference environment и семи
wheels. Пять исходных outputs нужны отдельно для сравнения. Ни одна сторона
не получает заранее восстановленный рабочий каталог в зачёт восстановления.

Для каждой стороны создать C1, связать сохранённый reference, затем сохранить
текущие условия C2 с C=2.0 без нового обучения. Удаляется только одноразовая
исходная рабочая копия. Восстановление получает точный исторический ID/revision
C1, не latest. Базовые ОС и Python уже установлены: их реконструкция не заявляется.

Разрешённые активы восстановления заранее перечисляются в setup.json:
объектное хранилище и метаданные core; Git/DVC metadata, локальный DVC remote,
MLflow SQLite/artifact root альтернативы. Новая рабочая копия и её cache
изначально пустые. Git может сохранять историю публичного кода; произвольное
извлечение данных из иных ревизий, домашней папки, исходного wheelhouse или
сетевых источников не входит в проверяемый путь восстановления.

В negative-копиях удаляется или портится единственный зарегистрированный
объект выбранного типа во всех разрешённых источниках текущего пути, а не
доказывается исчезновение всех возможных копий данных в мире. Другие копии
и caches явно учитываются. Если native-инструмент законно восстанавливает
объект из разрешённой резервной копии, это восстановление, а не пропущенный
отказ; незапланированная избыточность требует сохранить случай и уточнить
протокол до следующей попытки. Исходные evidence и store не изменяются.

## Общая проверка среды и численного результата

После получения материалов обе стороны сверяют весь inventory по SHA-256 и
размеру. Эта проверка общая и не приписывается исключительно одному продукту.
Нативные сообщения DVC/core сохраняются отдельно от заключения общего checker.
Далее создаётся новая venv без system-site-packages и устанавливаются только
семь восстановленных wheels: pip --no-index --no-cache-dir --require-hashes
--no-deps --only-binary=:all: с PIP_DISABLE_PIP_VERSION_CHECK=1.

Полный fingerprint из исходного environment.json проверяется существующим
Wine helper до обучения и по новым outputs после него; четыре thread limits
равны 1 согласно frozen Wine protocol. Несовпадение среды даёт failed либо
incomparable/blocked для соответствующей стадии, но не numerical pass.
Пайплайн неизменённый, phase=validation, C=1.0, фиксированные data/split/model.

Независимый oracle - функция oracle из examples/wine_catalog/validate_cycle.py
в закреплённом core, SHA-256 файла:
7130855433ba33f9cdd29ea9a2ab72fe62d129eaf07fad30fd421ba0e810c33d.
Она читает raw labels, split и predictions, независимо пересчитывает row IDs,
матрицы, support и четыре метрики через Fraction и сверяет source/repeat.
Критерий - точное равенство дискретных результатов и этих метрик, без нового
допуска. UUID, времена и другие ожидаемые различия outputs не требуют
побайтового равенства файлов; исходные и новые raw bytes сохраняются отдельно.

Во время каждого случая strace -f -yy -e trace=network,process наблюдает дерево
процессов восстановления/исполнения: execve/PID дополняют UUID как признак
нового запуска. Процесс запускается с закрытыми унаследованными дескрипторами,
кроме явно записанных stdin/stdout/stderr без сетевых соединений. Входящие
listen/accept не предусмотрены. При неоднозначной семье socket/FD, обрезанной
трассе или неподтверждённом завершении tracer результат unchecked, не offline
pass. Дополнительная trace=file может сохраняться как диагностика; сетевой
лог сам по себе не доказывает отсутствие неучтённых файловых чтений.
Разрешены локальные файловые операции
и локальные socket probes; исходящие AF_INET/AF_INET6 connect/send операции
выделяются в отчёт. Ожидаются отсутствие исходящего трафика и только объявленные
локальные источники. Это наблюдаемый offline-проход, не сетевая песочница.
User/network namespaces в текущем окружении недоступны. При трафике или
неполной трассировке offline не подтверждается; исход и причина сохраняются.

## Случаи, порядок и критерии

Один заранее заданный проход: четыре случая для каждой из двух конфигураций,
всего восемь случаев. Это проверка детерминированных инженерных свойств,
не выборка для вероятности успеха. Порядок: S0(core), S0(alternative), затем
S1(core), S1(alternative), S2(core), S2(alternative), S3(core), S3(alternative).
Каждый случай использует отдельную копию разрешённых активов и новый workdir.

| ID | Воздействие | Заранее заданный ожидаемый результат |
| --- | --- | --- |
| S0 | C2 существует, исходная workspace удалена; восстановить C1 | Все required bytes и условия C1 подтверждены; новая venv, фактическое успешное выполнение, новая попытка/source link, oracle pass, старая история неизменна |
| S1 | Удалён обязательный dataset blob, новый cache пуст | Missing/error до обучения, numerical unchecked, честная failed attempt либо явно неопределённая регистрация; прежние records/outputs неизменны |
| S2 | Тот же blob изменён с сохранением длины | Corrupt/integrity error до обучения, numerical unchecked; прежняя история неизменна; скрытый reuse старого результата запрещён |
| S3 | Удалён один из семи обязательных wheels | Missing dependency до обучения, numerical unchecked; без сетевого pip fallback и без выдачи готовности среды |

Точные одинаковые объекты и мутация закреплены в protocol-v1.json: dataset
wine/data/wine.data, 10782 bytes, SHA-256
6be6b1203f3d51df0b553a70e57b8a723cd405683958204f96d23d7cd6aea659.
S2 меняет byte offset 0 через XOR 1, оставляя длину; ожидаемый SHA-256
bd893782ef39cd49a95ae1ca8f002f7ae3419957cd8d8d1ffde0ae2e09782812.
S3 удаляет cloudpickle-3.1.2-py3-none-any.whl, 22228 bytes, SHA-256
9acb47f6afd73f60dc1df93bb801b472f05ff42fa6c84167d25cb206be1fbf4a.
Дескрипторы и ожидаемые hashes при порче не переписываются.

Границы ожидания стенда, а не оценки скорости: 300 s для отдельной стадии,
900 s для случая, 5 s на завершение собственного дочернего процесса перед
принудительной остановкой. Timeout даёт interrupted/blocked по известным
фактам, никогда succeeded. Ожидаемые negative продолжают заданную серию;
дефект стенда, неучтённый источник, неполная трасса или несопоставимая среда
останавливают серию с сохранением попыток. Эти guards не меняются по исходу.

Статусы разделены: materials, restored conditions/runtime, execution,
registration и numerical agreement. Неизвестное не становится success;
нечисловая метрика не превращается в ноль. Каждый случай получает внешний
attempt UUID независимо от модели identity инструмента. Альтернатива получает
новый MLflow run, source linkage и Git/DVC revision/ref. Core получает новый
operation/run с исходным snapshot/source_run_id. Невозможность создать иной
native snapshot при тех же условиях сама по себе не является ошибкой.

Успех negative означает ожидаемое обнаружение отказа, а не успешное обучение.
Если до resolve source запись ещё невозможна, явно указать её отсутствие;
не создавать фиктивный finished/succeeded. Исходы по стадиям важнее exit code.

## Что измеряется и откуда берётся вывод

| Вопрос | Первичные свидетельства | Критерий и граница вывода |
| --- | --- | --- |
| Восстановлены ли нужные условия? | C1/C2 revisions, resolved IDs, inventory, hashes, config и fingerprint | Исторический C1 без подмены C2; native resolution отдельно от checker |
| Было ли новое выполнение? | argv, exit, время, PID, новый Wine UUID и пять outputs | Реальный процесс и новый результат, не cached artifact |
| Согласуется ли результат? | Raw data/split/predictions, оба metrics.json, Fraction oracle | Exact equality только при сопоставимой среде; не оценка качества инструмента |
| Сохранилась ли история? | Прежние records/receipts, canonical MLflow source record, Git refs и хеши старых outputs до/после | Неизменность наблюдённой истории; не обещание транзакций SQL+artifacts или защиты от злонамеренного владельца |
| Обнаружены ли отказы до ML? | Native diagnostic, common checker, признак запуска процесса, failure record | Три заданных повреждения; каждый вывод привязан к механизму обнаружения |
| Что делает сам продукт? | Команды, документированный API, adapter source и сохранённые результаты | Native / common external checker / scenario adapter / unchecked; без общего балла |

У core native: CAS-проверка, snapshots/runs/source link, structural diff и
RecoveryPlan. Его repeat.py, подготовка venv, runtime helper и oracle внешние.
У альтернативы native: Git revisions, DVC materialization/pipeline/experiment
records и MLflow runs/metrics/artifacts. Связывание source_run_id со снимком,
inventory, проверка среды и общий итог - внешний адаптер. В обоих вариантах
общий Wine/oracle не становится собственной новой функцией инструмента.
MLflow tags/artifacts не объявляются неизменяемыми только потому, что наш
адаптер их не перезаписал. Отсутствующие измерения отмечаются unchecked.

## Сохранение попыток, изменения и приёмка

До первого случая стенд получает отдельный проверенный commit SHA. Сохранять
setup/software manifests, полный package freeze, argv/cwd/env allowlist,
stdout/stderr/exit, времена/PID, input/output hashes, trace, refs/IDs, стадии и
oracle в новом каталоге. Все попытки, включая setup errors и инфраструктурные
срывы, перечислять в attempts index. Полные приватные scratch/venv/cache не
публиковать; public evidence содержит малые структурированные результаты,
raw outputs и hashes. Диагностические пути можно нормализовать в публичной
копии с явной отметкой; raw outputs и их hashes не редактировать.

Установочные синтетические smoke не являются Wine trials. Неподдержанный
флаг на этой стадии - ограничение availability, не измеренный отказ Wine.
Автоматического повтора «до успеха» нет. При дефекте стенда сохранить попытку,
объяснить исправление, зафиксировать новый review/commit до следующего прохода;
предыдущая серия не исчезает. Внешняя блокировка остаётся blocked/unchecked,
не подменяется результатом. Если альтернатива не выполнена, #25 остаётся открытой.

Итог #25 требует проведённых случаев, прозрачных результатов и независимого
review. Обязательны Go test/race/vet/CLI build, Wine tests и затронутые проверки
платформы. В #26 входят итоговый технический отчёт, известные ограничения,
ссылки на primary evidence и проверка инструкции из чистой рабочей среды.
Работа не означает завершённый текст ВКР или утверждённый исследовательский вклад.
